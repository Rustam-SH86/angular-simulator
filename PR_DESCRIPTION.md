# Архитектурный рефакторинг Angular-приложения

## Что выбрано

### Архитектура: Feature-Based + Core/Shared

Приложение разделено по функциональным областям. `features` содержит пользовательские сценарии, `core` — единственную общеприложенческую инфраструктуру, а `shared` — переиспользуемые элементы без бизнес-зависимостей.

Внутри крупных feature используется локальное слоение:

- `pages` — компоненты маршрутов;
- `ui` — презентационные компоненты;
- `application` — facade и состояние;
- `data-access` — HTTP-сервисы и resolvers;
- `models` — типы конкретной feature.

### UI и логика: Facade Pattern + Component-Based Design

Компоненты страниц больше не обращаются к HTTP API напрямую. Они получают готовое состояние и вызывают пользовательские операции через facade. Компоненты в `ui` отвечают только за отображение, формы, inputs и outputs.

Например, `PostsComponent` делегирует загрузку, удаление и обновление `PostsFacade`. Благодаря этому из компонента удалены HTTP-вызовы, состояние списка и ручные вызовы `ChangeDetectorRef.detectChanges()`.

### Состояние: Signals + RxJS на асинхронной границе

Основное состояние интерфейса хранится в Signals:

- текущий пользователь;
- списки users, posts и products;
- фильтры, пагинация и loading;
- корзина и вычисляемые суммы;
- тема, loader и сообщения.

RxJS сохранён там, где он подходит лучше: HTTP-запросы, interceptors, debounce полей ввода, отмена и композиция асинхронных операций.

### Методология: TDD для безопасного рефакторинга

Поведение application-слоя фиксируется unit-тестами facade. Добавлены тесты для users и posts. Angular schematics теперь создают spec-файлы по умолчанию, чтобы новые компоненты и сервисы не появлялись без тестовой заготовки.

## Какие проблемы решены

- Файлы сгруппированы по функциональным областям вместо хранения компонентов, сервисов, моделей и инфраструктуры в общих корневых папках `app`.
- Users перенесён в самостоятельную feature вместо нескольких несвязанных корневых папок.
- UI-компоненты posts больше не управляют API и состоянием вручную.
- `UserService` и пустой `PostService` заменены facade с понятной ответственностью.
- Состояние интерфейса переведено на Signals, чтобы во всех feature использовать один понятный подход.
- Auth разделён на `AuthApiService` и `AuthFacade`.
- Доступ к token storage проходит через единую storage-абстракцию.
- Feature routes загружаются лениво через отдельные `*.routes.ts`.
- Состояние страниц ограничено route-provider, когда оно не должно жить глобально.
- Корзина намеренно оставлена root-singleton, чтобы сохраняться при переходе между каталогом, карточкой товара и `/cart`.
- Удалены неиспользуемые учебные файлы, пустой сервис.
- Подписка на изменение поискового поля автоматически очищается при закрытии страницы товаров, что предотвращает утечки памяти.
- Loading и ошибки обрабатываются facade/interceptors, а не дублируются в компонентах.

## Почему не альтернативы

### Почему не глобальная Layered Architecture

Глобальные папки `components`, `services` и `models` снова смешали бы users, posts, products и auth. Локальные слои внутри feature сохраняют направление зависимостей, но не разрывают одну функциональность между всем проектом.

### Почему не Redux/NgRx

В приложении нет сложного глобального потока событий, множества зависимых bounded contexts или требований к time-travel/debug tooling. Redux добавил бы actions, reducers, selectors и effects без соразмерной пользы.

### Почему не только RxJS

Большая часть состояния синхронна и непосредственно используется шаблонами. Signals уменьшают количество `BehaviorSubject`, `async` pipe и ручных подписок. RxJS остаётся на асинхронной границе, где нужны его операторы.

### Почему не только singleton-сервисы

Root singleton для состояния каждой страницы сохранял бы устаревшие данные после выхода из feature и постепенно превращал сервисы в глобальное хранилище. Route-scoped facades уничтожаются вместе с маршрутом. Исключение — корзина и core-сервисы, которым действительно нужен жизненный цикл всего приложения.

### Почему не DDD

Приложение в основном выполняет CRUD над внешними API и пока не содержит сложных агрегатов, доменных событий и бизнес-инвариантов. Полный DDD создал бы лишние repository/entity/value-object слои. Feature boundaries оставляют возможность перейти к DDD позже, если доменная сложность появится.

### Почему TDD, а не OOD как основная методология

OOD используется при проектировании facade и сервисов, но сам по себе не защищает рефакторинг от регрессий. TDD даёт проверяемую обратную связь при переносе файлов и ответственности.
